## 重构：本地模式「磁盘即事实来源」对应模型（用户新方案，优于加 ID）
- 用户判断正确：本地模式身份此前完全靠 name/path 字符串，内存 tab 用会话级 nanoid 不落盘，重命名/删除后侧边栏与标签页对不上。
- 方案：本地所有操作（重命名/删除/新建/文件夹重命名）先落到本地磁盘，再统一用 `refreshScan(true)` 从磁盘重读、投影回网页；只保留「已打开标签页的磁盘位置」这**一处**必要更新。外部磁盘改动由 FileSystemObserver → handleFsChanges 同样走 refreshScan 投影（免费同步）。
- 改动：
  - `useNoteStore.js`：本地笔记补齐 `dirPath`（此前缺失→嵌套笔记对应不上）；新增 `updateLocalNoteLocation(oldFilename,oldDirPath,newFilename,newDirPath)`（重命名笔记时更新已打开 tab 一处）与 `updateLocalNotesDirPath(oldDirPath,newDirPath)`（重命名文件夹时批量改已打开 tab 的 dirPath 前缀）。
  - `Sidebar.vue`：`handleOpenLocalNote` 打开磁盘笔记补 `dirPath`，去重匹配改为 filename+dirPath（避免同名不同目录误判）。
  - `FolderTree.vue`：renameLocalNote / addNoteInFolder 改为 `refreshScan(true)`（移除 setNodeContents 定向刷新与多处手动变量同步）；runLocalOp 默认深刷新；startRename 文件夹分支重命名后调用 updateLocalNotesDirPath；handleFsChanges 简化为失效缓存+深刷新，并处理外部删除(removeLocalNote)/移动(moved→updateLocalNoteLocation)已打开 tab。
- 已知取舍：文件夹重命名会使该文件夹在侧边栏折叠（无 ID，key 随路径变而重挂载）。

## 修补：观察器处理「外部文件夹重命名」边缘情况（用户确认需要）
- 背景：上一版 handleFsChanges 只处理单文件 moved（自带 old+new 锚点，可靠），但**文件夹级 moved**被 isMd 挡掉未处理；且若浏览器把文件夹重命名报成 `deleted`+`created`，原代码会把内部已打开 tab 误当删除关掉。
- 重写 `handleFsChanges`（`src/components/FolderTree.vue`）：
  1. 由 `rootItems` 构建 `knownDirSet`（当前树含旧名，刷新前有效）。
  2. 单文件 `moved`(isMd) → 精确 `updateLocalNoteLocation`（同前）。
  3. 文件夹级 `moved`（旧路径在 knownDirSet）→ 记 `folderMoves`，末调用 `updateLocalNotesDirPath(oldDirPath,newDirPath)` 批量重映射 tab 的 dirPath。
  4. `deleted`+`created` 同名 .md 配对识别为「移动」(pairedMoves) 而非删除，避免误关 tab；无配对的 deleted 才是真删除 → `removeLocalNote`。
  5. 覆盖浏览器对文件夹重命名的两种上报方式（级联单文件 moved / 文件夹级 moved / delete+create）。
- 覆盖仍不完全处：深层未扫过的嵌套文件夹（不在 knownDirSet、也无级联 moved）外部改名时 tab 仍指向旧路径——极端边缘，保留原行为。

## 修复：本地重命名（含根目录）后侧边栏不刷新
- 用户实测：**根目录**笔记改名后侧边栏不刷新（磁盘✅、标签页✅）。反证：根笔记走 `rootFiles`(←`rootItems`)→`getNoteTitle`=`resolveLocalTitle(map,name)`；`rootItems` 未刷新→仍含旧名 `'OldName.md'`→`getNoteTitle` 因 map 无 `'OldName'` 键回退 `stripMd`=旧名。故断点在 `refreshScan` 未执行 `rootItems.value=mergeItems`。
- 根因：`refreshScan` 顶部 `if (scanPromise) return scanPromise` 并发守卫——在途浅刷新（onMounted/watch 调 `refreshScan()` 浅扫）会拦截并重用其 Promise，把 `refreshScan(true)` 的深刷新降级成浅刷新（deep 标志被丢弃），导致根 `mergeItems` 不跑；且 scanPromise 若卡死则永久不刷新。
- 修复（`src/components/FolderTree.vue`）：
  1. 守卫改为 `scanning`+`pendingDeep` 机制：在途扫描时若收到 deep 请求则记 `pendingDeep`，扫描 `finally` 结束后补一次 `refreshScan(true)`；`scanning` 必在 finally 清除，不会永久卡死。
  2. `renameLocalNote`：改名后不再单纯依赖 `refreshScan(true)`，改为**确定性直接刷新所在目录**——`invalidateCache(dirPath)`+`listDirectoryContents(dirPath)`+（`dirPath` 非空则 `setNodeContents`，否则 `rootItems.value=mergeItems(rootItems.value, contents)`），绕开并发守卫，保证改名层一定被刷到（根与嵌套都覆盖）。
- 附带：Sidebar:258 `folderTreeRef.value?.refreshScan` 悬停显示 `any` 是 TS 未推断组件实例类型，非运行时 bug（`defineExpose({refreshScan,resetAndScan})` 已正确暴露，手动刷新可用）。

## 再修：侧边栏改名仍不刷新（用户实测根目录改名依旧不更新）
- 分析：侧边栏根笔记链路 `rootItems→rootFiles(computed)→模板 v-for(file in rootFiles)→getNoteTitle(file.name)`。`getNoteTitle` 查 `localNotesMap`(noteList) 取 title，查不到回退 `stripMd(filename)`——只要 `file.name` 变新名，显示必为新名。故「显示旧名」≡「rootItems 仍含旧名」≡「`rootItems.value=新数组` 这次没真正拿到新名」。
- 推断真正的脆弱点：`renameLocalNote` 此前依赖 `invalidateCache`+`listDirectoryContents`+`mergeItems` 从磁盘重读；若 `renameLocalFile` 删旧文件未真正生效（磁盘残留旧名），重读又把旧名读回覆盖刚改好的，或磁盘重读时序不稳导致未拿到新名——这些都会让侧边栏卡在旧名，且与「刷新也没用」吻合。
- 修复（`src/components/FolderTree.vue`）：
  1. 新增 `renameTreeItem(dirPath,oldName,newName)`：沿 `dirPath` 在内存树定位父目录、把匹配 `oldName` 的条目改名，整棵根引用重建（保证响应式）。这是**确定性**的立即更新，不依赖磁盘重读时序。
  2. `renameLocalNote` 改为：先 `renameTreeItem` 立即改内存树（侧边栏立即更新）→ 再 `invalidateCache`+`listDirectoryContents` 对账，但**仅当 disk 确实含新名(`contents.some(c=>c.name===newName)`)时才覆盖**，防止旧文件残留把新名覆盖回去。
  3. 加诊断 `console.log('[renameLocalNote] disk=... oldStill=... newHas=...')`，用于确认磁盘重读是否真拿到新名（若仍失败可据此判断是旧文件未删还是缓存问题）。
- 结论：立即改名由内存树保证；磁盘对账仅在干净时生效，不会回退。构建验证 `.build-verify-renamefix` EXIT 0。

## 修复：本地模式删除文件夹报 NotFoundError
- 症状：本地模式删除文件夹提示 `NotFoundError: A requested file or directory could not be found`。
- 根因：`useLocalModeStore.deleteLocalFolder(dirPath)` 算法错误——它 `for (part of parts) current=getDirectoryHandle(part)` 一路走进**目标文件夹内部**（current 变成要删的文件夹本身），最后又 `current.removeEntry(parts[last])` 试图从文件夹内部按自身名字删自己，必然 NotFoundError。
- 修复（`src/stores/useLocalModeStore.js`）：改为走到**父目录**（`getOrCreateDirectory(parentPath)`），再 `parent.removeEntry(folderName, { recursive: true })` 递归删除整个文件夹；并对老旧实现不支持 recursive 选项（抛 TypeError）的情况降级为逐层删除子项再删自身。`invalidateCache(parentPath)` 失效父目录缓存。
- 构建验证：`npm run build -- --outDir .build-verify-delfolder` EXIT 0（仅 chunk 体积无关警告），验证目录已删。

## 修复：本地模式刷新后侧边栏排序乱跳
- 症状：本地模式无任何磁盘变动、连点刷新按钮，侧边栏笔记/文件夹顺序会改变。
- 根因：侧边栏顺序直接取自 `FileSystemDirectoryHandle.entries()` 的**原始枚举顺序**（`useLocalModeStore.listDirectoryContents` 只 push `{name,kind}`、不排序）；该 API 规范**不保证枚举顺序稳定**，多次调用可能给出不同排列。渲染层 `rootFiles`/`rootFolders`（FolderTree）与 `FolderItem` 本地 `childFolders`/`items` 仅 `filter` 无排序；`FolderItem:180` 的 `b.updateTime-a.updateTime` 对本地项（无 `updateTime` 字段）算成 NaN 是空操作。
- 方案（用户确认按**文件名 A→Z** 确定性排序，不取 mtime、零额外 I/O、贴近资源管理器默认视图）：在 4 处 computed 末尾加 `.sort((a,b)=>a.name.localeCompare(b.name))`：
  - `src/components/FolderTree.vue:170-171` 的 `rootFolders` / `rootFiles`。
  - `src/components/FolderItem.vue` 的 `childFolders`（本地分支 map 后）与 `items` 本地分支（map 后）。在线分支 `b.updateTime-a.updateTime` 不变。
- 保留「文件夹区→文件区」分组；`:key` 仍按 `name`，排序不会触发无谓重挂载。
- 构建验证：`npm run build -- --outDir .build-verify-sortname` EXIT 0（仅 chunk 体积无关警告）；`.gitignore` 的 `.build-verify-fresh*` 散行合并为 `.build-verify*`。
